## 計算量の整理

以降，頂点数を $n$，辺数を $m$ とする．また，1 フレーム中に実行される描画・当たり判定・力学モデル更新を主な対象とする．

### 現状の概算

| 処理                        |                   現状の計算量 | 主な原因                                               |
| ------------------------- | -----------------------: | -------------------------------------------------- |
| 辺追加時の重複判定                 |                   $O(m)$ | `edges.iter().any(...)` による線形探索                    |
| 隣接頂点列挙                    |           $O(mn)$ 程度まで悪化 | 全辺走査に加え，隣接頂点 ID から `vertices.iter().find(...)` を行う |
| 力学モデルの反発力計算               |                 $O(n^2)$ | 各頂点について全頂点を走査                                      |
| 力学モデルの辺による引力計算            | $O(nm + n^2m)$ 程度まで悪化し得る | 各頂点で `neighbor_vertices` を呼ぶため                     |
| 描画用 `vertex_positions` 構築 |                   $O(n)$ | 毎フレーム `HashMap` を作る                                |
| 描画用 `edge_count` 構築       |                   $O(m)$ | 毎フレーム `HashMap` を作る                                |
| 各辺の終点半径取得                 |                  $O(mn)$ | 各辺ごとに `snapshot.vertices.iter().find(...)`         |
| 辺描画全体                     |       $O(n + m + mn)$ 程度 | 補助データ構築と各辺ごとの頂点探索                                  |
| 辺 hit-test                |                   $O(m)$ | 全辺に対して距離計算                                         |
| 曲線辺 hit-test              |           $O(m \cdot I)$ | 各曲線辺で Newton 法を最大 `I` 回実行                          |
| 頂点描画順ソート                  |            $O(n \log n)$ | 毎フレーム `z_index` でソート                               |
| 補グラフ生成                    |             $O(n^2 + m)$ | 隣接行列相当を作り，全頂点対を見る                                  |
| 近似直径下界                    |               $O(n + m)$ | 隣接リスト構築後，BFS を各成分で定数回行う                            |

ここで，`I` は Newton 法の反復回数である．現在の実装では定数回に制限されているため，実用上は定数として見てよい．ただし，曲線辺の数が多い場合は定数倍が大きくなる．

特に問題になりやすいのは，次の 3 つである．

* `neighbor_vertices` を各頂点から呼ぶことによる力学モデルの悪化
* `render_edges` で各辺ごとに頂点探索をすることによる $O(mn)$
* 辺 hit-test で全辺に対して距離計算を行うことによるフレームごとの $O(m)$

### Phase 1 後: `adjacency` 導入後

`Graph` に `adjacency: Vec<Vec<usize>>` を持たせると，隣接頂点列挙の計算量が改善される．

| 処理                  |                      改善前 |          改善後 |
| ------------------- | -----------------------: | -----------: |
| 隣接頂点列挙              |           $O(mn)$ 程度まで悪化 | $O(\deg(v))$ |
| 全頂点に対する隣接辺処理        | $O(nm + n^2m)$ 程度まで悪化し得る |       $O(m)$ |
| `rebuild_adjacency` |                       なし |   $O(n + m)$ |
| 力学モデルの辺による引力計算      |                       重い |       $O(m)$ |

ここで，$\deg(v)$ は頂点 $v$ の次数である．

`adjacency` の再構築は $O(n + m)$ である．毎フレームではなく，グラフ構造が変わったタイミングだけ実行すればよい．

したがって，力学モデルの 1 step は，反発力計算をそのままにした場合でも，おおよそ次のようになる．

$$
O(n^2 + m)
$$

反発力計算の $O(n^2)$ は残るが，隣接頂点列挙に由来する余分なコストを削減できる．

### Phase 2 後: `edge_set` 導入後

`edge_set: HashSet<(usize, usize)>` を持たせると，辺の存在判定を平均 $O(1)$ にできる．

| 処理                 |    改善前 |       改善後 |
| ------------------ | -----: | --------: |
| 辺の重複判定             | $O(m)$ | 平均 $O(1)$ |
| 辺追加                | $O(m)$ | 平均 $O(1)$ |
| `rebuild_edge_set` |     なし |    $O(m)$ |

`edge_set` の再構築は $O(m)$ である．これも毎フレームではなく，構造変更時にだけ行う．

無向グラフでは，辺キーを正規化する．たとえば `u-v` と `v-u` を同一視するために，`(min(u, v), max(u, v))` をキーにする．この正規化は $O(1)$ である．

### Phase 3 後: `GraphSnapshot` の補助インデックス化後

`GraphSnapshot` に `vertex_index` と `edge_count` を持たせると，描画時の探索が減る．

| 処理                    |                改善前 |             改善後 |
| --------------------- | -----------------: | --------------: |
| `vertex_positions` 構築 |             $O(n)$ | snapshot 作成時に統合 |
| `edge_count` 構築       |             $O(m)$ | snapshot 作成時に統合 |
| 各辺の終点頂点探索             |            $O(mn)$ |       平均 $O(m)$ |
| 辺描画全体                 | $O(n + m + mn)$ 程度 |   平均 $O(n + m)$ |

`snapshot()` 自体は，頂点と辺を走査するため $O(n + m)$ である．ただし，この中で補助インデックスをまとめて作れば，描画側で再度 `HashMap` を作る必要がなくなる．

特に，各辺ごとの `snapshot.vertices.iter().find(...)` をなくせる点が大きい．これにより，辺描画まわりの $O(mn)$ を平均 $O(m)$ に落とせる．

### Phase 4 後: 辺 hit-test の粗判定導入後

bounding box による粗判定を入れても，最悪計算量は $O(m)$ のままである．しかし，正確な距離計算を行う辺数を $k$ に減らせる．

ここで，$k$ をマウス近傍の候補辺数とする．

| 処理           |            改善前 |         改善後 |
| ------------ | -------------: | ----------: |
| 直線辺 hit-test |         $O(m)$ |  $O(m + k)$ |
| 曲線辺 hit-test | $O(m \cdot I)$ | $O(m + kI)$ |

bounding box 判定自体は各辺 $O(1)$ なので，全辺を見る限り最悪 $O(m)$ は残る．しかし，Newton 法や正確な線分距離計算を呼ぶ回数は $k$ に減る．

将来的に grid / quadtree などの空間インデックスを導入すれば，候補辺取得をおおよそ次のようにできる可能性がある．

$$
O(\log m + k)
$$

ただし，動的に頂点が移動するアプリでは，空間インデックスの更新コストも考慮する必要がある．力学モデルで毎フレーム頂点位置が変わる場合，辺の bounding box も毎フレーム変わるため，最初は単純な bounding box 判定だけで十分である．

### Phase 5 後: 頂点描画順ソートの差分化後

現在，頂点描画時に毎フレーム `z_index` でソートしている場合，計算量は $O(n \log n)$ である．

`vertex_draw_order` をキャッシュし，`z_index` が変わったときだけ更新するようにすれば，通常フレームでは $O(n)$ の走査だけで済む．

| 処理       |                   改善前 |                             改善後 |
| -------- | --------------------: | ------------------------------: |
| 頂点描画順の決定 | $O(n \log n)$ / frame | 通常 $O(1)$，dirty 時 $O(n \log n)$ |
| 頂点描画     |                $O(n)$ |                          $O(n)$ |

描画自体は各頂点を描く必要があるため $O(n)$ からは下がらない．ただし，毎フレームのソートを避けられる．

### Phase 6 後: 力学モデルの整理後

`positions` / `velocities` を一時配列に分離し，`neighbor_ids` を使うと，力学モデル 1 step の計算量は次のようになる．

$$
O(n^2 + m)
$$

内訳は以下である．

| 処理         |      計算量 |
| ---------- | -------: |
| 位置・速度配列の作成 |   $O(n)$ |
| 反発力計算      | $O(n^2)$ |
| 辺による引力計算   |   $O(m)$ |
| 位置・速度の書き戻し |   $O(n)$ |

つまり，最終的には $O(n^2 + m)$ である．

この段階では，反発力計算の $O(n^2)$ が支配的である．より大規模なグラフに対応するには，次の近似が必要になる．

| 手法           |                     期待される計算量 | 備考                    |
| ------------ | ---------------------------: | --------------------- |
| grid 近似      | $O(n + m)$ から $O(nc + m)$ 程度 | セル近傍だけを見る．実装は比較的容易    |
| Barnes-Hut 法 |         $O(n \log n + m)$ 程度 | 精度と速度のバランスがよいが実装はやや重い |
| ランダムサンプリング   |                  $O(ns + m)$ | 各頂点につき $s$ 個だけ反発力を計算  |
| 反発力の間引き      |                フレームあたりの計算を削減 | 見た目の安定性とトレードオフ        |

まずは $O(n^2 + m)$ の素直な実装でよい．その後，頂点数 1000 以上で重い場合に近似法を検討する．

## 改善前後の全体像

### 通常フレーム，アニメーションなし

改善前は，描画用補助データ構築，各辺ごとの頂点探索，頂点ソート，辺 hit-test が重くなる．概算では次のようになる．

$$
O(n + m + mn + n \log n + m)
$$

支配的には，辺ごとの頂点探索による $O(mn)$ が問題になる．

改善後は，`GraphSnapshot` の補助インデックス化と描画順キャッシュにより，おおよそ次の形になる．

$$
O(n + m)
$$

ただし，hit-test で全辺を見る場合は $O(m)$ が残る．描画自体も頂点・辺を描くため $O(n + m)$ は必要である．

### 通常フレーム，アニメーションあり

改善前は，力学モデルの反発力計算に加えて，隣接頂点列挙の重さが乗る．概算では次のようになる．

$$
O(n^2 + \text{heavy-neighbor-search} + \text{rendering})
$$

改善後は，隣接リストにより辺による引力計算が $O(m)$ になり，描画も $O(n + m)$ に近づく．

$$
O(n^2 + m)
$$

この時点では，反発力計算の $O(n^2)$ が支配的である．

### グラフ構造変更時

構造変更時には，補助データを再構築する必要がある．

| 補助データ                        |        再構築コスト |
| ---------------------------- | ------------: |
| `adjacency`                  |    $O(n + m)$ |
| `edge_set`                   |        $O(m)$ |
| `GraphSnapshot.vertex_index` |        $O(n)$ |
| `GraphSnapshot.edge_count`   |        $O(m)$ |
| `vertex_draw_order`          | $O(n \log n)$ |

これらを毎フレームではなく，必要なときだけ再構築するのが重要である．

## 優先度への計算量面からの補足

最優先は `adjacency` の導入である．これは力学モデルの隣接頂点列挙を改善し，全頂点に対する辺由来の力計算を $O(m)$ に近づけられる．

次に `GraphSnapshot` の補助インデックス化が重要である．これは描画時の $O(mn)$ を $O(n + m)$ に落とせるため，アニメーションの有無に関係なく効く．

`edge_set` は毎フレーム処理には直接効かないが，辺追加やグラフ構築を安定して高速化できる．実装上も `adjacency` と相性がよい．

辺 hit-test の bounding box は，最悪計算量は変わらないが，重い距離計算の回数を減らせるため，体感速度に効きやすい．

`z_index` ソートの差分化は，頂点数が多い場合には効くが，優先度はやや低い．描画自体が $O(n)$ で必要なため，まずは $O(mn)$ や力学モデルの余分な探索を削る方がよい．
